# Database

PostgreSQL 18 on Neon. The supplied database was **empty** when this project started (only the
`public` schema, no tables), so nothing needed backing up. All store tables live in their own
schema, **`store`**, and the migration journal in **`store_migrations`**, so the database can be
shared later without name clashes. Migrations are generated by drizzle-kit from
`src/server/db/schema.ts` into `drizzle/` and applied with `npm run db:migrate` (one transaction).

## Tables

| Area | Tables |
|---|---|
| Catalogue | `categories`, `collections`, `products`, `product_collections`, `product_colors`, `product_images`, `product_variants` |
| Inventory | `inventory_transactions` (append-only ledger) — stock lives on `product_variants.stock` |
| Shopping | `carts`, `cart_items`, `customers`, `orders`, `order_items`, `order_events`, `payments`, `shipping_methods` |
| Admin | `users`, `sessions`, `settings` (store info, policies, size guide as JSON), `audit_logs` |
| Operations | `rate_limits`, `ai_usage`, `newsletter_subscribers` |

## Invariants enforced by the database

- Money is integer tögrög; `products.base_price > 0`, `price_override IS NULL OR > 0`.
- **Every colour × size is its own variant** (`unique(product_id, color_id, size)`) with its own
  unique SKU and stock; `stock >= 0` is a CHECK constraint, so overselling fails even outside
  the application.
- Order lines snapshot product name, slug, colour, size, SKU, image and **unit price**;
  `line_total = unit_price × quantity` and `orders.total = subtotal + shipping_fee` are checked.
  Changing a product price never rewrites an existing order.
- Each stock change writes `inventory_transactions(delta, stock_after, reason, order_id, actor)`.
  The integration suite asserts that every variant's stock equals the sum of its ledger.

## Seed

`npm run db:seed` is idempotent: it inserts only what is missing (by slug, code, e-mail or
order number) inside one transaction and never overwrites, so admin edits survive re-runs.
It loads 8 categories, 6 collections (3 rule-based: new / women / men), 30 products,
168 variants, delivery methods, policies, the size guide, the demo user, the owner account
(from `ADMIN_*`), and 14 sample orders. Sample customers use phone numbers beginning `0000`
so they can never belong to a real subscriber; sample payments are `simulated`.

## Backups

Before any destructive change: `npm run db:backup` is reserved for a dump script; on Neon,
create a branch (instant copy-on-write snapshot) from the console before migrating.
